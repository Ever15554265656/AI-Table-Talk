## 1. 背景与产品目标

### 1.1 一句话定位

「AI Panel Studio」是一个**本地运行的 AI 圆桌演播厅**：用户输入任意话题与专家人数，系统调用大模型现场生成「1 位主持人 + N 位立场互斥的专家」，用户确认阵容后进入演播厅，观看一场由 AI 主持、专家自主抢答/反驳/补充的**实时直播式讨论**，过程中持续沉淀共识与分歧，最终由主持人以自然语言收尾。

### 1.2 为什么需要它（对应 L12–L15 的痛点）

| 原始痛点（L12–L15） | 本产品的解法 | 对应需求 |
|---|---|---|
| 视角单一：单一 AI 对话立场单一，缺少对抗性思考 | 强制生成**立场互斥**的多专家阵容，并允许「反驳」意图优先于礼貌补充 | R2 / R3 |
| 异步割裂：多次轮询不同 AI，上下文割裂、无法互相碰撞 | 单一共享 transcript 作为**唯一事实来源**，每轮发言都基于全文上下文的最近窗口 | R3 / R6 |
| 过程不可见：只有终局输出，缺少思考过程的实时感 | 专家状态小窗（待机/准备发言/发言中 + 公开关注点）+ 共识分歧边走边更新 | R4 / R5 |
| 议题管理混乱：多议题的上下文与结论难以并行隔离 | 讨论级隔离：`discussion_id` 贯穿数据、事件、Prompt 与连接池 | R9 |

### 1.3 目标用户与核心诉求（对应 L7–L10）

| 用户群体 | 特征 | 其在本产品中的成功路径 |
|---|---|---|
| 知识工作者 / 研究人员 | 时间有限，需要多角度审视议题 | 5 分钟内看完一场 20 轮讨论，直接读「共识 + 分歧 + 总结」 |
| 产品 / 决策人员 | 方案评审前想预演各方立场与争议 | 关注「分歧栏」是否命中自己没想到的反对意见 |
| 教育 / 内容创作者 | 需要可回放、有叙事性的「虚拟专家访谈」 | 已结束讨论可只读回放完整 transcript 与总结 |

## 2. 范围界定

### 2.1 In Scope（本期必做）

- 讨论列表首页、发起讨论向导、阵容确认页、演播厅单页（Transcript / 专家小窗 / 共识分歧 / 控制条）。
- 后端：讨论状态机、嘉宾生成、发言调度、共识与分歧提炼、总结生成、SSE 推流、多讨论并行隔离。
- 数据：SQLite 落库、初始化脚本、≥5 条预设样例数据（含话题与对应嘉宾阵容）。
- 质量：核心三模块单元测试 + 隔离集成测试 + 端到端测试。
- 文档：PRD（本文）、ER 图、API 文档、README、Prompt 记录（≥5 段/四范式）、工作流说明。

### 2.2 Out of Scope（本期明确不做，避免范围膨胀）

| 不做的事 | 原因 |
|---|---|
| 语音合成 / 语音输入 | 原始需求未要求，且不影响「演播厅沉浸感」的评分点 |
| 用户注册、登录、权限体系 | 本地单机应用；隐私与多用户鉴权不在考核范围 |
| 观众在直播中发弹幕/提问、影响讨论走向 | 原始需求仅要求「加入/观察」，未要求互动输入（见 DECISIONS D-03） |
| 展示真实 chain-of-thought / 推理链 | 明确禁止（L22），仅展示「公开思考摘要」 |
| 跨重启的实时续推（进程崩溃后从断点继续发言） | 降级为「重启后房间标记为中断并提供基于落库数据的只读回放」（见 C-06） |
| 移动端原生 App、离线 PWA | 只需响应式 Web |

## 3. 角色与用户故事

| 角色 | 说明 | 权限 |
|---|---|---|
| 发起者（Host Operator） | 创建讨论、生成并确认阵容、控制开演/暂停/结束 | 全量 |
| 围观者（Observer） | 从首页进入已有讨论，只读观看实时推流 | 只读（不可发控制指令） |
| 系统（System） | 调度器、共识提炼器、总结生成器 | 内部进程 |

> 本期无鉴权，角色是**行为语义**而非权限系统（见 2.2）。

### 3.1 用户故事（Given / When / Then）

**US-1 发起讨论**
Given 我打开首页，When 我点击「发起新讨论」并填入话题「远程办公是否降低了团队创新力」与专家人数 4，Then 系统在 3 秒内返回 1 位主持人 + 4 位专家（姓名、职业/Title、立场、专属颜色），并停在我的确认页等待我决定。

**US-2 调整阵容**
Given 我看到生成的阵容，When 我发现其中两位专家立场过于接近并点击「重新生成」，Then 系统按上一次话题重新生成一套阵容，且不会污染我尚未确认的任何状态。

**US-3 确认并开演**
Given 阵容令我满意，When 我点击「确认阵容并进入演播厅」，Then 页面跳转演播厅，主持人立即说出开场白，3 秒内至少一位专家的状态小窗由「待机」切换为「准备发言」。

**US-4 观察讨论实况**
Given 讨论正在进行，When 某位专家开始发言，Then 其小窗状态变为「发言中」，Transcript 追加一条带姓名、职业/Title 与其专属颜色的发言，且发言长度不超过 2 句。

**US-5 实时把握共识与分歧**
Given 讨论已进行 6 轮以上，When 我看向右侧共识/分歧区，Then 我能看到已形成的共识条目与至少一条明确对立的分歧（含对立双方与支撑发言引用），且它们不是等讨论结束后才出现的。

**US-6 旁听他人讨论**
Given 首页存在一场状态为「演播中」的讨论，When 我点击进入，Then 我从当前进度开始接收实时推流（含历史 transcript），且我看到的控制按钮为禁用态。

**US-7 观看总结**
Given 讨论轮次用尽或我点击「结束讨论」，When 主持人完成总结，Then 页面展示自然语言总结（含共识、分歧、结论建议），页面任何位置都不出现 JSON 原文。

## 5. 功能需求详述

> 每条需求固定四段式：**需求描述 / 交互与规则 / 数据与接口 / 验收标准（AC）**。AC 采用可测表述，直接对应后续 pytest / Playwright 用例。

### 5.1 R1 首页：讨论列表 / 加入观察 / 发起新讨论

**来源**：`REQUIREMENTS.md` L19

**需求描述**
首页是全站入口，必须展示当前所有正在进行的讨论列表；用户可从列表**加入/观察**已有讨论，也可**发起新讨论**。

**交互与规则**
1. 列表数据源为 `GET /api/discussions`，展示字段：话题、状态徽标、席位数（`1 位主持人 + N 位专家`）、已产生发言数、最近更新时间（相对时间如「2 分钟前」）。
2. 默认排序：按状态优先级 `live > ready > casting > ended`，同优先级内按 `updated_at` 倒序。
3. 每行提供主操作：`ready` → 「确认阵容」；`live` → 「进入旁听」；`ended` → 「查看回放」；`failed` → 「重试生成」。
4. 「发起新讨论」为页面主 CTA（primary button），固定可见，点击进入创建面板（抽屉/模态，不跳空白页）。
5. 列表为空时展示空态插画/文案 + 引导按钮。
6. 状态文案中文化映射：`draft 草稿 / casting 生成阵容中 / ready 待确认 / live 演播中 / summarizing 生成总结中 / ended 已结束 / failed 生成失败`。

**数据与接口**
- 读：`GET /api/discussions?scope=all|active`
- 写：`POST /api/discussions`（见 R2）
- 列表刷新：前端每 5 秒轮询一次（可被下一次手动操作打断），不要求全局 SSE 频道。

**验收标准**

| AC | 验收标准 |
|---|---|
| AC-1.1 | 打开应用根路由 `/`，无需任何操作即渲染讨论列表，且数据来自后端 `GET /api/discussions`（测试可断言请求发生）。 |
| AC-1.2 | 每个列表项至少展示：话题、中文状态徽标、`1+N` 席位说明、发言数、相对更新时间。 |
| AC-1.3 | 列表排序满足 `live > ready > casting > ended`，同级按 `updated_at` 倒序（后端排序 + 前端不再二次打乱）。 |
| AC-1.4 | 数据库无讨论时，页面展示空态文案与「发起新讨论」按钮，不出现空白页或 `undefined`。 |
| AC-1.5 | 点击 `ready` 项进入阵容确认页；点击 `live` 项进入演播厅旁听；点击 `ended` 项进入只读回放；点击 `failed` 项可重试生成。 |
| AC-1.6 | 「发起新讨论」在 1280px 与 375px 视口下均可见且可点击（不被遮挡、不需横向滚动）。 |
| AC-1.7 | 另开一个浏览器标签创建一个新讨论后，原标签页在 ≤10 秒内自动出现该讨论，无需手动刷新。 |
| AC-1.8 | 所有状态徽标文案均为中文，且与 §5.1 规则的映射一致（自动化断言文案字典）。 |
| AC-1.9 | 列表容器自身 `overflow-y: auto`，条目增加到 30 条时页面整体仍不产生纵向滚动（`document.scrollingElement.scrollHeight <= clientHeight`）。 |
| AC-1.10 | 后端不可用时，页面展示中文错误提示与「重试」，不白屏、不抛未捕获异常。 |

### 5.2 R2 嘉宾生成与阵容确认

**来源**：`REQUIREMENTS.md` L20

**需求描述**
用户输入**话题**与**专家人数**（默认 4），系统调用大模型动态生成 **1 位主持人 + N 位专家**，展示每位嘉宾的**姓名、职业/Title、立场、专属颜色标识**，用户**确认后**方可进入演播厅。

**交互与规则**
1. 创建表单：话题（必填，裁剪首尾空白后长度 1–200） + 专家人数（整数 2–8，默认 4，步进器 + 快捷值 3/4/6）。
2. 提交后讨论进入 `casting`，前端显示「正在组建专家席…」骨架态，生成按钮进入 loading 并防重复提交（禁用 + 幂等键）。
3. 生成结果必须满足：恰好 `N+1` 个席位，其中 `role=host` 恰好 1 个。
4. **立场多样性硬约束**：每位专家输出 `stance_axis ∈ {support, oppose, conditional, neutral}`；校验要求 `support` 与 `oppose` 各至少 1 位，否则进入重试；重试 2 次仍不满足则由本地确定性补位（把最接近中立的专家改写为 opposite 轴并标注兜底来源）。
5. **颜色约束**：同场讨论内颜色唯一，取自已定义调色板（≥8 色，均通过深色底 ≥4.5:1 对比度），由**后端**分配并落库；前端禁止自行随机取色。
6. 确认页：主持人卡片单独置顶并标注「主持人」，专家按席位顺序平铺，每卡含颜色标识条/圆点、姓名、职业/Title、立场一句话。
7. 操作：`重新生成`（复用同话题同人数，替换未确认阵容，不新建讨论记录）、`确认阵容`、`返回首页`。
8. 确认即开演：确认后状态 `ready → live`，并立刻触发主持人开场（见 R3）。
9. 未确认的讨论不可被他人当作直播进入。

**数据与接口**
- `POST /api/discussions` → `{topic, expert_count}` → 201 `{id, status:"casting"}`
- `GET /api/discussions/{id}` → 含 `panelists[]`
- `POST /api/discussions/{id}/regenerate` → 200（替换 panelists）
- `POST /api/discussions/{id}/confirm` → 200 `{status:"live"}`；非 `ready` 状态返回 409

**LLM 调用契约（Prompt 四要素）**

| 要素 | 定义 |
|---|---|
| 角色 | 「圆桌演播厅选角导演」，需产出**立场互斥**的专家阵容 |
| 输入快照 | 话题、专家人数、已用姓名（避免重复）、色调板枚举、禁止事项 |
| 输出 schema | `{host:{name,title,stance,stance_axis}, experts:[{name,title,stance,stance_axis}]}`，无额外字段，纯 JSON 对象 |
| 失败兜底 | Pydantic 校验失败 → 带错误回灌重试（≤2 次）→ 仍失败用本地模板阵容并把 `source=mock_fallback` 落库 |

**验收标准**

| AC | 验收标准 |
|---|---|
| AC-2.1 | 话题为空/全空白时提交被拦截，前端与后端均返回中文提示；长度 201 字符同样被拦截（前后端规则一致，有单测覆盖边界 0/1/200/201）。 |
| AC-2.2 | 专家人数可设 2–8，越界输入被拒（前端禁用按钮 + 后端 422）；默认值确为 4。 |
| AC-2.3 | 生成成功后 `panelists` 数量恰为 `N+1`，且 `role=host` 恰 1 个（后端断言 + 单测覆盖 N=2/4/8）。 |
| AC-2.4 | 每位嘉宾均含非空 `name`、`title`、`stance`、`stance_axis`、`color`；任一字段缺失即视为生成失败并触发重试。 |
| AC-2.5 | 同场讨论内 `color` 两两不同，且均来自服务端调色板；前端渲染的颜色与 `panelists[].color` 严格一致（无随机/无色板外取值）。 |
| AC-2.6 | 生成的专家阵容中 `support` 与 `oppose` 至少各 1 位；用固定 Mock fixture 构造「全 support」的坏输出时，系统必须触发重试或兜底，最终结果仍满足该约束（单测覆盖）。 |
| AC-2.7 | 确认页展示主持人置顶 + 专家列表，每张卡片同时可见姓名、职业/Title、立场、颜色标识（无 hover 也能看见）。 |
| AC-2.8 | 点击「重新生成」后 `discussion.id` 不变、话题与人数不变、`panelists` 被整体替换（旧席位不再出现），且列表页讨论数量不增加。 |
| AC-2.9 | 确认成功后 3 秒内收到主持人开场发言（`utterance.created` 且 `role=host, turn_type=opening`）。 |
| AC-2.10 | 未确认（`ready`/`casting`）的讨论被他人访问 `/discussions/{id}` 时，只展示确认页或 409，不可接收直播事件流。 |
| AC-2.11 | LLM 抛错或连续两次结构不合法时，讨论置为 `failed`，前端展示中文错误原因与「重试生成」，已填话题不丢失（表单回填）。 |
| AC-2.12 | `casting` 期间重复提交（双击/重放请求）只创建 1 条讨论记录（幂等键 + 后端唯一约束验证）。 |
| AC-2.13 | Mock Provider 下整条「创建→出阵容」链路耗时 ≤ 1s（E2E 稳定性要求）。 |

### 5.3 R3 演播厅模式：主持人 + 专家自主发言

**来源**：`REQUIREMENTS.md` L21

**需求描述**
进入演播厅后，由 AI 主持人负责**开场、追问、串联、总结**；专家根据当前 transcript **自主决定发言顺序**（举手 / 抢答 / 补充 / 反驳），每次发言**控制在 1~2 句**；**严禁机械式轮流发言**。

**交互与规则**

1. **角色分工**
   - 主持人 `role=host`：`opening`（开场，全场首条，必有）→ `followup`（追问，可就某位专家的观点施压）→ `bridge`（串联，阶段性收束并引出新角度）→ `closing`（总结，见 R7）。
   - 专家 `role=expert`：只能产出 `raise`（提出/举起新论点）、`counter`（反驳他人）、`supplement`（补充他人）。

2. **发言权分配（Floor Control）**——这是「非轮流」的实现核心
   每一轮由一次独立的调度调用决定「下一位发言者」，**调度与生成分离**（两步 LLM 调用），调度阶段只产出决策，不产出正文：

   | 调度输入 | 说明 |
   |---|---|
   | 话题 | 讨论主题 |
   | 席位表 | 每位专家的姓名/Title/立场/`stance_axis`/已发言次数 |
   | 最近 K 条发言 | K=8，含发言者与正文（截断至 160 字/条） |
   | 会话统计 | 当前轮次、上一位发言者、已被打断次数、主持人上次介入距今轮数 |

   | 调度输出（严格 schema） | 说明 |
   |---|---|
   | `next_speaker_id` | 必须是席位表中的 id |
   | `intent` | `raise` / `counter` / `supplement` / `host_followup` / `host_bridge` |
   | `focus` | ≤40 字的**公开关注点**（用于专家小窗，非推理链） |
   | `quoted_utterance_id` | 反驳/补充时必填，指向被回应的发言 |

3. **服务端否决与抑制规则（防退化，必须在代码里强制，不能只靠 Prompt）**
   - R-1 同一专家连续发言不得超过 **2** 次；命中则否决，改选次优候选。
   - R-2 若近 4 次发言严格按席位顺序递增推进（即「轮流转」征兆），**强制打散**：改选与上一位立场轴对立且发言次数最少的专家。
   - R-3 若某专家在 `3 × N` 轮后仍 0 次发言，下一轮赋予优先权（保证公平下限，但以「优先权」而非「顺序」实现）。
   - R-4 主持人介入节奏：每 3~5 轮必须出现一次 `host_followup` 或 `host_bridge`；且主持人不得连续介入 2 次。
   - R-5 调度返回的 `next_speaker_id` 非法（不在席位表）时，服务端本地按「最少发言 + 立场对立」选择，**不中断直播**。

4. **发言长度硬约束**：正文必须 **1~2 句**。后端后处理：按中文句末标点（`。！？!?…`）切句，超过 2 句则保留前 2 句并补句号，同时置 `truncated=true`；超过 120 字同样硬截断。Prompt 中亦明确「最多两句、口语化、不要列举」。

5. **节奏与轮次**：默认 `max_turns=20`（可配 12~40）；相邻两条发言间隔 1.2–2.5s（Mock 模式 150–300ms 以加速测试）；达到上限自动进入 `summarizing`。

6. **控制条**：`暂停 / 继续 / 结束讨论 / 返回首页`；暂停时调度器停止推新发言（已流式中的那条可完成）。

7. **演播厅布局**：顶部为话题 + 状态 + 轮次进度；中部为主舞台 Transcript；右侧为专家席 + 共识分歧栏（见 §6.4 三档响应式）。

**数据与接口**
- `POST /api/discussions/{id}/start`（确认后自动调用）/ `pause` / `resume` / `end`
- 事件：`utterance.created`、`panelist.state`、`turn.advanced`（见 §11）
- 落库：`utterances(discussion_id, seq, speaker_id, intent, content, truncated, created_at)`

**LLM 调用契约（Prompt 四要素）**

| 要素 | 定义 |
|---|---|
| 角色 | 「演播厅现场导播」（调度阶段）／「正在发言的某专家」（生成阶段，携带其姓名、Title、立场作为人格锚点） |
| 输入快照 | 调度：话题 + 席位表 + 最近 8 条发言 + 统计；生成：自身人格 + 被引用的发言 + 最近 6 条发言 + 意图与关注点 |
| 输出 schema | 调度：`{next_speaker_id, intent, focus, quoted_utterance_id}`；生成：`{content}`（string，不含 JSON 之外的任何结构） |
| 失败兜底 | 校验失败重试 ≤2 次；仍失败 → 调度走 R-5 本地规则，生成走模板句（如「这一点我需要补充一句：……」）并标记 `degraded=true` |

**验收标准**

| AC | 验收标准 |
|---|---|
| AC-3.1 | 确认阵容后 3 秒内出现第一条发言，且其 `role=host`、`intent=opening`；开场白引用话题原词。 |
| AC-3.2 | 每条发言前均存在一次调度决策（可在 DB / 事件中审计），且**代码中不存在按席位数组顺序展开发言的实现**（单测 + 代码评审项）。 |
| AC-3.3 | 20 轮标准场次中，至少出现 1 次「与上一位发言者在席位顺序上相隔 ≥2」的跳跃，且至少出现 2 条 `intent=counter` 与 1 条 `intent=supplement`（Mock fixture 固定的确定性用例）。 |
| AC-3.4 | 任意 4 次连续发言不得构成「按席位顺序完整递增」的模式（单测直接断言 R-2 打散逻辑被触发并生效）。 |
| AC-3.5 | 同一专家连续发言次数全场 ≤2（断言 DB `seq` 序列）。 |
| AC-3.6 | 每条发言的句数 ≤2（按中文句末标点计），且无发言长度 >120 字；被截断时 `truncated=true`。 |
| AC-3.7 | 20 轮场次中：主持人开场 1 次、`followup ≥1`、`bridge ≥1`；主持人从不连续两条发言。 |
| AC-3.8 | 席位数 N 时，在 ≥`3×N` 轮后每位专家发言次数 ≥1。 |
| AC-3.9 | 当前发言者的专家小窗与 Transcript 条目**同时**呈现高亮（同色边框/发光 + 淡入动画），切换延迟 ≤1s。 |
| AC-3.10 | 点击「暂停」后 1 秒内不再产生新发言（事件流静默），点击「继续」后恢复推进。 |
| AC-3.11 | 达到 `max_turns` 或点击「结束」后状态进入 `summarizing`，且总结只生成一次（重复触发为幂等）。 |
| AC-3.12 | 调度 LLM 返回非法 `next_speaker_id`（Mock 注入）时，直播不中断，服务端本地选出合法发言者并继续（单测覆盖）。 |
| AC-3.13 | 生成阶段返回超长文本（Mock 注入 5 句）时，落库内容已被截断为 2 句，且前端只显示 2 句。 |

### 5.4 R4 专家状态小窗

**来源**：`REQUIREMENTS.md` L22

**需求描述**
每位专家有独立小窗，**实时**显示 Agent 运行状态（待机 / 准备发言 / 发言中）与**当前关注点或公开思考摘要**；**不得展示真实的隐藏 chain-of-thought**。

**交互与规则**
1. 状态枚举（与后端一致，三态，不多不少）：`idle 待机` / `preparing 准备发言` / `speaking 发言中`。
2. 状态流转：被调度选中 → `preparing`（展示 `intent` 与 `focus`）→ 文字流式开始 → `speaking` → 发言结束 1s 内 → `idle`。
3. 小窗内容：颜色标识 + 姓名 + Title + 状态徽标 + 关注点文本（≤40 字，无内容时展示「旁观中…」）。主持人单独以「主持台」形式呈现当前行为（开场/追问/串联/总结）。
4. **禁止 CoT**：对外契约中只允许 `focus`（公开关注点）字段；不存在 `reasoning` / `chain_of_thought` / `thought` / `scratchpad` 等字段；Prompt 明确要求「给出一句话的公开关注点，不要输出推理过程」。
5. 同一时刻最多 1 位专家处于 `speaking`。
6. 小窗在窄屏折叠为横向滚动的状态条（仍保留三态与关注点）。

**数据与接口**
- 事件：`panelist.state`（`{panelist_id, state, intent, focus, updated_at}`）
- 初值：进入演播厅时由快照事件一次性下发全部席位状态。

**验收标准**

| AC | 验收标准 |
|---|---|
| AC-4.1 | 演播厅中每位专家（含主持人）均有独立小窗，含姓名、Title、颜色标识。 |
| AC-4.2 | 状态文案仅出现「待机 / 准备发言 / 发言中」三种，且随 SSE 事件在 1 秒内更新。 |
| AC-4.3 | `preparing` 与 `speaking` 期间小窗可见「关注点」文本（≤40 字）；无内容时展示占位文案而非空白。 |
| AC-4.4 | 全量 API 响应与前端状态树中不存在 `reasoning`/`chain_of_thought`/`thought`/`scratchpad` 字段（契约快照测试断言）。 |
| AC-4.5 | `speaking` 状态仅在该专家发言进行期间存在；发言结束后 1 秒内回到 `idle`（断言事件序列 idle→preparing→speaking→idle 完整闭合）。 |
| AC-4.6 | 任意时刻处于 `speaking` 的专家数 ≤1（事件日志断言）。 |
| AC-4.7 | 375px 视口下三态与关注点仍可见（折叠为横条），无内容被截断到不可读。 |
| AC-4.8 | 主持人区域展示其当前行为标签（开场/追问/串联/总结），并在总结阶段显示「正在整理结论」。 |

### 5.5 R5 实时共识与分歧

**来源**：`REQUIREMENTS.md` L23

**需求描述**
讨论**过程中持续**从发言中提炼共识与分歧，**实时更新**对应区域；**不允许等到讨论结束后才生成**。

**交互与规则**
1. **触发节奏**：每新增 `3` 条专家发言触发一次增量提炼（可配 2–4）；提炼在后台串行执行（同一讨论同一时刻仅 1 个提炼任务，后到触发合并为 1 次），**绝不阻塞发言调度**。
2. **增量而非全量重算**：输入 = 现有条目快照 + 本轮新增发言；输出 = 更新后的完整条目列表（保留既有 `id`，使前端可做「更新」而非「重建」动画）。
3. **条目结构**
   - 共识 `ConsensusItem`：`id、statement(≤60字)、support_utterance_ids[]、updated_at`
   - 分歧 `DivergenceItem`：`id、topic(≤30字)、position_a{label, speaker_ids[]}、position_b{label, speaker_ids[]}、support_utterance_ids[]、updated_at`
4. **校验与防幻觉**：所有 `support_utterance_ids` 与 `speaker_ids` 必须存在且属于**本场讨论**；非法 id 直接剔除该引用；若剔除后无引用则丢弃该条目。
5. **数量上限**：共识 ≤6 条、分歧 ≤4 条；超限时保留被引用次数最多者并合并语义相近条目（由 LLM 给 `merge_into` 提示，服务端执行合并）。
6. **UI**：右栏（或窄屏底部抽屉）分「共识」「分歧」两个 Tab/分区，各自独立滚动；新增/更新条目高亮 3 秒后淡出；条目内引用可点击定位到 Transcript 对应发言。
7. **终态冻结**：`ended` 后条目只读，不再更新。

**数据与接口**
- 表：`consensus_items`、`divergence_items`（均带 `discussion_id`）
- 读：`GET /api/discussions/{id}/insights` → `{consensus:[], divergence:[]}`
- 事件：`insight.updated`（`{kind:"consensus"|"divergence", items:[...]}`，整组下发便于幂等对齐）

**LLM 调用契约（Prompt 四要素）**

| 要素 | 定义 |
|---|---|
| 角色 | 「讨论纪要分析员」 |
| 输入快照 | 话题 + 现有共识/分歧条目 + 本轮新增发言（含 id 与发言者） |
| 输出 schema | `{consensus:[{id?, statement, support_utterance_ids}], divergence:[{id?, topic, position_a:{label, speaker_ids}, position_b:{label, speaker_ids}, support_utterance_ids}]}` |
| 失败兜底 | 校验失败重试 ≤1 次；仍失败**保留上一次结果**并记录 `insight_degraded=true`，直播继续 |

**验收标准**

| AC | 验收标准 |
|---|---|
| AC-5.1 | 第 3 条专家发言之后 ≤3 秒内，`GET /insights` 至少返回 1 条共识或分歧（Mock 确定性用例）。 |
| AC-5.2 | 一场 20 轮讨论中 `insight.updated` 事件出现 ≥3 次，且首次出现时刻远早于讨论结束（断言：`first_insight_at < ended_at` 且发言数 < 一半）。 |
| AC-5.3 | 每条共识/分歧至少含 1 个有效 `support_utterance_id`，且该 id 属于本场讨论（后端校验 + 单测注入跨房间 id 必须被剔除）。 |
| AC-5.4 | 分歧条目必含 `position_a` 与 `position_b`，双方 `speaker_ids` 各 ≥1 且无交集。 |
| AC-5.5 | 反复提炼不产生重复条目（同一 `statement` 只出现一次）；合并后条目数不增加。 |
| AC-5.6 | 共识 ≤6 条、分歧 ≤4 条上限被强制生效（单测注入 10 条时被裁剪）。 |
| AC-5.7 | 新增/更新条目在 UI 上高亮 ≤3 秒后恢复常态；同一 `id` 更新不产生重复 DOM 节点。 |
| AC-5.8 | 点击条目引用可滚动定位到对应 Transcript 发言并高亮 3 秒。 |
| AC-5.9 | 提炼 LLM 抛错时直播不中断、旧条目保留、`degraded` 标记被记录（单测覆盖）。 |
| AC-5.10 | `ended` 状态下不再产生 `insight.updated` 事件（断言事件流）。 |

### 5.6 R6 现场 Transcript

**来源**：`REQUIREMENTS.md` L24

**需求描述**
Transcript 显示**发言人姓名与职业/Title**，用**与专家一致的颜色**区分；**不显示「举手」等内部事件**。

**交互与规则**
1. 每条发言渲染为气泡/条目：`颜色竖条或圆点 + 姓名 + 职业/Title + 正文`；主持人条目带「主持人」标识且视觉可区分。
2. **颜色同源**：颜色值一律取自 `panelists[].color`（后端落库），与专家小窗、席位卡完全一致。
3. **不展示内部事件**：`intent`（举手/抢答/反驳/补充）、`state`、调度决策、`quoted_utterance_id` 等技术字段**一律不渲染**；Transcript 中也不出现系统提示（如「讨论已暂停」）。
4. **滚动策略**：容器 `overflow-y:auto`；仅当用户位于底部（距底 <40px）时自动跟随新发言；用户上滑后停止跟随并显示「回到最新」浮动按钮（新消息计数）。
5. **完整性**：进入/刷新后通过快照 + 事件重放补齐全部历史，按 `seq` 升序渲染，无重复、无空洞。
6. **空态**：`live` 但暂无发言时显示「等待主持人开场…」。

**数据与接口**
- 读：`GET /api/discussions/{id}/transcript?after_seq=`（快照补拉）
- 事件：`utterance.created`（含完整条目，可幂等 upsert by `seq`）

**验收标准**

| AC | 验收标准 |
|---|---|
| AC-6.1 | 每条发言同时可见发言人姓名、职业/Title 与颜色标识；颜色 hex 与 `panelists[].color` 字符串相等。 |
| AC-6.2 | 页面文本中不出现「举手」「抢答」「准备发言」「发言中」「调度」等内部事件/意图词汇（E2E 对 Transcript 区域文本做黑名单断言）。 |
| AC-6.3 | Transcript 区域不出现 `{`、`}`、`"key":` 形式的 JSON 片段。 |
| AC-6.4 | 用户处于底部时，新发言自动滚入可视区；用户上滑到距底 >40px 后不再自动滚动，且出现「回到最新（N 条）」按钮，点击后回到底部并清零计数。 |
| AC-6.5 | Transcript 容器独立滚动，页面整体不产生纵向滚动（`scrollHeight <= clientHeight`）。 |
| AC-6.6 | 讨论进行到第 8 条时刷新页面，恢复后条目数一致、顺序与 `seq` 严格递增、无重复条目（幂等 upsert 断言）。 |
| AC-6.7 | `live` 且无发言时显示「等待主持人开场…」文案。 |
| AC-6.8 | `ended` 讨论可完整只读回放（刷新后仍在），且无任何写入控件。 |
| AC-6.9 | 主持人条目与专家条目在视觉上可区分（不同底色/边框/标签），但在窄屏下都不发生横向溢出。 |

### 5.7 R7 结束总结

**来源**：`REQUIREMENTS.md` L25

**需求描述**
讨论结束时，**主持人以自然语言进行总结**；**禁止将 JSON 原文显示到页面上**。

**交互与规则**
1. **触发**：达到 `max_turns` 或用户点击「结束讨论」→ 状态 `summarizing` → 生成总结 → `ended`。
2. **生成输入**：全部发言（按 seq）+ 最终共识/分歧条目 + 话题。
3. **输出 schema（严格）**：`{summary_sections: [{heading, body}]}`，其中 `heading ∈ {共识、分歧、结论建议}`，`body` 为含标点的中文自然语言段落（不含代码块、不含字段名、不含引号包裹的键值对）。
4. **双呈现**：① 作为主持人最后一条发言（`turn_type=closing`）进入 Transcript；② 演播厅右侧/底部「讨论总结」卡片展示分段文本。
5. **幂等**：每场讨论只生成一次；重复请求返回已存结果（`summary` 表按 `discussion_id` 唯一）。
6. **兜底**：LLM 失败或校验不过 → 用模板把已有共识/分歧拼成自然语言（必须仍是完整中文段落，且标记 `degraded=true`）。
7. **前端渲染纪律**：只渲染 `heading` 与 `body` 字符串；任何情况下都不 `JSON.stringify` 后上屏。

**数据与接口**
- 读：`GET /api/discussions/{id}/summary`
- 事件：`summary.created`
- 表：`summaries(discussion_id UNIQUE, sections_json, degraded, created_at)`

**验收标准**

| AC | 验收标准 |
|---|---|
| AC-7.1 | 点击「结束讨论」后 ≤10 秒（Mock ≤1s）页面展示总结；期间状态显示「正在生成总结」。 |
| AC-7.2 | 页面全文（含总结卡片与 Transcript）不出现 `{`、`}`、`"` 包裹的键值结构，不出现 `summary_sections`、`heading` 等字段名（E2E 正则断言）。 |
| AC-7.3 | 总结包含三部分中文段落：共识、分歧、结论建议，且每部分 ≥1 句完整句子。 |
| AC-7.4 | 总结内容与共识/分歧区一致：至少 1 条总结表述与某条共识 `statement` 存在 ≥10 字连续重合（幻觉抑制的弱验证）。 |
| AC-7.5 | 主持人收尾发言出现在 Transcript 末条（`turn_type=closing`，`role=host`）。 |
| AC-7.6 | 重复调用结束接口不重新生成（`created_at` 不变，内容一致），`summaries` 表对本讨论仅 1 行。 |
| AC-7.7 | LLM 失败时仍产出中文自然语言兜底总结，不含 JSON，前端不报错（单测注入异常覆盖）。 |
| AC-7.8 | `ended` 后重新进入该讨论，可直接看到历史总结（持久化生效）。 |
